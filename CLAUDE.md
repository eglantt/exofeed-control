# CLAUDE.md — ExoFeed Control

Этот файл загружается автоматически в начале каждой сессии Claude Code в этом репозитории. Он заменяет необходимость каждый раз объяснять контекст заново.

## Что это за приложение

**ExoFeed Control** — учёт кормления, линек и содержания животных в террариумном хозяйстве (Алматы). Один самодостаточный HTML-файл (`index.html`, актуальная версия — см. `<title>` в файле) — весь HTML/CSS/JS в одном месте, без сборки, без внешних зависимостей (кроме опционального PWA service worker). Работает офлайн, вся база — в `localStorage` браузера. Развёрнуто на GitHub Pages, установлено как PWA на нескольких телефонах. Пользователи — 3-4 человека, работают по очереди, передают базу через ручной экспорт/импорт JSON.

## КРИТИЧЕСКИ ВАЖНО — непрерывность базы данных

Это правило нарушать нельзя ни при каких обстоятельствах — пользователь придаёт этому первостепенное значение, это не преувеличение, а буквальный факт живой рабочей базы:

1. У живой базы — версионный ключ `localStorage`: `exofeed_db_vX.Y.Z` (переменная `CURRENT_DB_KEY`). **При каждой новой версии, для любой правки, даже косметической:**
   - `CURRENT_DB_KEY` обновляется на новую версию;
   - **предыдущая** версия добавляется первой в массив `legacyKeys` (список всех обратно совместимых ключей для чтения при загрузке — код идёт по списку по порядку и берёт первый найденный).
   - Без этого шага база пользователя "слетит" при замене файла на GitHub Pages.
2. Есть отдельные, **не завязанные на версию** ключи (не требуют добавления в `legacyKeys`): `exofeed_archive`, `exofeed_ui_collapsed_locs`, `exofeed_engineer_pin`, `exofeed_custom_species`, `exofeed_db_modified_at`.
3. Миграция старых структур данных — в функциях `normalizeCell()`, `normalizeAnimal()`, `migrateBlock()`. Каждое новое поле добавляется туда с `if (x === undefined) x = ...` — старые записи без этого поля получают безопасное значение по умолчанию.
4. **Каждая новая версия обязана** пройти тест "старая база версии N-1 корректно читается версией N" — это не опционально.
5. `<title>`, `.version-tag`, `CURRENT_DB_KEY`, `legacyKeys` обновляются **всегда**, для любой версии.

## Модель данных (актуальная на v1.7.0)

```
db = [ location {
  id, name,
  blocks: [ block (стеллаж) {
    id, name, type,
    rows: [ row (полка) {
      cells: [ cell {
        label, isService, width, tempLog: [{timestamp, value}],
        animals: [ animal {
          species, gender, age, birthMonth, birthYear,
          notesLog: [{timestamp, text}],
          feed_logs: [{
            timestamp,        // момент, когда КО был ПРЕДЛОЖЕН — НЕ перезаписывается при разрешении "на ночь" (v1.6.0)
            date, type, sizeNum, sizeTitle, weightUnit, count,
            eatenCount,       // null пока не разрешено ("оставлен на ночь"), иначе число
            status,           // 'Съедено' | 'Отказ' | 'Частично' | 'Оставлен на ночь' | 'Срыгивание'
            refusalReason, comment, forced,
            koState,          // v1.6.0: 'prekilled' | 'thawed' | 'live' — состояние КО на момент подачи
            utilized,         // v1.6.0: true/false/null(ещё не разрешено) — идёт ли КО в расход (см. ниже)
            resolvedAt        // v1.6.0: момент утренней фиксации результата (не совпадает с timestamp)
          }],
          shed_logs: [{date, status, timestamp}],
          shed_status
        } ]
      } ]
    } ]
  } ]
} ]

archiveDb = [{ id, animal, reason, reasonText, archivedAt, originLocName, originBlockName, originAddress }]
```

Адрес ячейки (`A1`, `B3`...) **не хранится** — вычисляется на лету по позиции в массивах (`rowLetter()`, `getCellAddress()`, `locateCellPosition()`).

### Логика утилизации КО (v1.6.0) — "Расход КО"

- Предубит/разморозка → утилизирован (`utilized: true`) **всегда**, независимо от исхода.
- Живой + съеден (полностью/частично) → утилизирован.
- Живой + не тронут (`eatenCount === 0`) → при утренней фиксации доп. вопрос "жив/погиб": жив → **не** утилизирован (можно переиспользовать для другого кормления обычной новой записью, без связи между записями в базе), погиб → утилизирован.
- Срыгивание → утилизирован всегда.
- В отчётах колонка называется **"Расход КО"** (не "Утилизация" — переименовано в v1.7.0).

## Ключевые архитектурные решения (не переизобретать, если попросят похожее)

- **PIN на инженерный режим** — защита только от случайного нажатия, не от целенаправленного обхода (статичный клиентский файл, пользователь честно предупреждён). Структурные/деструктивные действия — под `class="edit-ui"`, видны только в инженерном режиме.
- **Календарь и подсветка по дате** — `calendarPreview`, временно перекрашивает реальный стеллаж, не дублирует схему.
- **Массовое кормление** (`massFeedState`) — ограничено ОДНИМ стеллажом одновременно, осознанно.
- **Массовая утренняя проверка** (v1.6.0, `morningCheckState`) — тоже один стеллаж, но НЕ через выбор ячеек галочками (это разные по природе задачи): список уже известных записей "оставлено на ночь" собирается сам, у каждой строки — чекбокс + кнопка "Отметить выбранное как съедено полностью" для ускорения, для остального — разворачивание строки.
- **Открытие ячейки** — нативное событие `click`, не ручное отслеживание жеста. Кастомный `pointerdown/move/up` — только для drag-and-drop в инженерном режиме (`attachCellDragHandlers`).
- **Перестановка локаций/стеллажей** — кнопки ▲/▼, сознательно НЕ drag-and-drop.
- **Крестик закрытия модалок** — инжектится `initModalCloseButtons()` во все `.modal` при старте.
- **Отчёты** — генерируются как отдельный самодостаточный HTML через `wrapReportDocument()`. `showReportModal(title, bodyHtml, filename, downloadBodyHtml?)` — необязательный 4-й параметр для отчётов с интерактивными элементами (выпадающие списки, кнопки копирования), которые не имеют смысла в статичном скачиваемом файле; если не передан — используется `bodyHtml` для обоих случаев.
- **Общая логика подсчёта отчётов** — `aggregateFeedingData(loc, startMs, endMs)` используется и отчётом за скользящую неделю (`openWeeklyReport`, `endMs = Infinity`), и отчётом за календарную неделю (`openCalendarWeekReport`, границы понедельник–воскресенье). Рендер вынесен в `renderTypeSummaryTable`/`renderSpeciesSummaryTable`/`renderChronoTable` — переиспользуются, чтобы правки не расходились между отчётами.
- Русские склонения — `pluralizeRu(n, one, few, many)`.

## Порядок работы

1. **Крупные/неоднозначные фичи** — сначала план, уточняющие вопросы (не больше одного за раз, если можно). Не писать код, пока не получено явное "пиши код" + подтверждён номер версии.
2. **Простые точечные правки** — план на 2-3 предложения, без затягивания.
3. **Каждая новая версия**: `<title>`, `.version-tag`, `CURRENT_DB_KEY`, `legacyKeys`, версия в `README.md` — всегда, для любой правки.
4. Пользователь заливает `index.html` на GitHub Pages (или это происходит через merge в `main`, если настроен деплой из ветки) — каждая версия должна пережить это обновление без потери данных.

## Тестирование (обязательный ритуал перед сдачей версии)

`bash` + Node.js + `jsdom` (`npm install jsdom`). После **каждого** значимого блока правок:

1. Извлечь `<script>` блоки, прогнать `node --check`.
2. jsdom-тесты через реальные DOM-события (`dispatchEvent(new win.MouseEvent('click', {bubbles:true}))`), не прямые вызовы функций — так ловятся баги в проводке событий.
3. Тест миграции: данные ПРЕДЫДУЩЕЙ версии в `localStorage`, прогнать загрузку — сверить поле-в-поле.
4. Полный регресс: создание локации/стеллажа/животного, drag-and-drop, календарь, архив, поиск, импорт бэкапа.
5. **Рекомендация**: держать тестовые скрипты в репозитории (например, `tests/test_vX.Y.Z.js`), а не создавать с нуля в каждой сессии — в отличие от чата, здесь есть постоянный доступ к репозиторию, этим стоит пользоваться. При правках, затрагивающих общую логику (как рефакторинг отчётов в v1.7.0), явно проверять, что старые тесты на предыдущие версии всё ещё проходят.

### Особенности jsdom, уже отловленные (не наступать на те же грабли)

- `new JSDOM(...)` обязательно с `url: 'http://localhost/'`, иначе `localStorage` кидает `SecurityError`.
- `element.innerText` в jsdom **не работает** ни на чтение, ни на запись (тихо ничего не делает) — используй `.textContent`. В коде приложения `showReportModal` использует `innerText` для заголовка — это осознанно не трогалось, при тестировании заголовка проверяй что-то другое (например, `window.currentHtmlReportFilename`), а не `textContent` этого элемента.
- В файле есть `document.write()` (генерация опций года рождения), рассчитанный на исполнение ВО ВРЕМЯ парсинга документа (как в браузере). Если нужно засеять `localStorage` до того, как отработает код инициализации базы — используй `beforeParse(win) { ... }` в опциях `new JSDOM(html, {...})` с `runScripts: 'dangerously'`, а НЕ `runScripts: 'outside-only'` + ручной `eval` скриптов после полной загрузки — это стирает весь документ повторным `document.write`.
- Верхнеуровневые `let`/`const` в `<script>` (`db`, `archiveDb`, `isLocked`, `CURRENT_DB_KEY`...) — **не** становятся свойствами `window`, в отличие от объявлений `function`. Читать/писать их можно только через `win.eval('varName')` / `win.eval('varName = ...')`. Рабочий паттерн для записи сложных объектов: `win['__tmp_x'] = value; win.eval('x = window.__tmp_x;')`.
- `URL.createObjectURL` не реализован — стабить вручную (`win.URL.createObjectURL = () => 'blob:mock'`).
- Для pointer-based drag-тестов — стабить `el.setPointerCapture = () => {}`.
- `setInterval` (тикающие часы) держит процесс Node живым — обязательно `process.exit(0)` в конце тестового скрипта.

## Файлы репозитория

- `index.html` — основное приложение.

- `README.md` — инструкция по деплою, версия в шапке обновляется при каждом релизе.

## Отложенные направления (НЕ начинать без явного запроса и отдельного обсуждения)

Обсуждались, но не реализуются в текущей архитектуре без отдельного решения пользователя:

- **Синхронизация между устройствами** — рассматривались варианты (свой PHP+MySQL хостинг, облачный диск, Firebase/Firestore). Текущее направление симпатий пользователя — Firebase, документ на локацию (не на животное), с закреплением локаций за конкретными пользователями через `assignedUserIds` и Security Rules; структурные правки — только у администратора, без разбивки документа локации на части (проверка прав только на уровне интерфейса, та же философия, что и у нынешнего PIN). Это большая архитектурная работа, требует отдельной сессии планирования — не начинать реализацию без явного запроса и подтверждённого плана.
- **Англоязычный форк** — статический перевод текущего приложения без слоя переключения языков, отдельный репозиторий, независимая нумерация версий.

Если пользователь просит продолжить любое из этих направлений — сначала свериться с ним, что план не изменился с момента последнего обсуждения (мог устареть), прежде чем писать код.
