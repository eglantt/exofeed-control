# CLAUDE.md — ExoFeed Control

Этот файл загружается автоматически в начале каждой сессии Claude Code в этом репозитории. Он заменяет необходимость каждый раз объяснять контекст заново. **Этот файл выдаётся заново вместе с каждой новой сборкой** — актуализировать его нужно в том же ответе, где отдаётся обновлённый `index.html`, а не откладывать на потом.

## Что это за приложение

**ExoFeed Control** — учёт кормления, линек, инкубации кладок и содержания животных в террариумном хозяйстве (Алматы). Один самодостаточный HTML-файл (`index.html`, актуальная версия — см. `<title>` в файле) — весь HTML/CSS/JS в одном месте, без сборки, без внешних зависимостей (кроме опционального PWA service worker). Работает офлайн, вся база — в `localStorage` браузера. Развёрнуто на GitHub Pages, установлено как PWA на нескольких телефонах. Пользователи — 3-4 человека, работают по очереди, передают базу через ручной экспорт/импорт JSON.

## КРИТИЧЕСКИ ВАЖНО — непрерывность базы данных

Это правило нарушать нельзя ни при каких обстоятельствах — пользователь придаёт этому первостепенное значение, это не преувеличение, а буквальный факт живой рабочей базы:

1. У живой базы — версионный ключ `localStorage`: `exofeed_db_vX.Y.Z` (переменная `CURRENT_DB_KEY`). **При каждой новой версии, для любой правки, даже косметической:**
   - `CURRENT_DB_KEY` обновляется на новую версию;
   - **предыдущая** версия добавляется первой в массив `legacyKeys` (список всех обратно совместимых ключей для чтения при загрузке — код идёт по списку по порядку и берёт первый найденный).
   - Без этого шага база пользователя "слетит" при замене файла на GitHub Pages.
2. Есть отдельные, **не завязанные на версию** ключи (не требуют добавления в `legacyKeys`, читаются/пишутся напрямую по своему постоянному имени):
   - `exofeed_archive` (`ARCHIVE_KEY`) — архив выбывших животных;
   - `exofeed_archive_clutches` (`CLUTCH_ARCHIVE_KEY`, с v1.8.0) — архив завершённых кладок;
   - `exofeed_ui_collapsed_locs` (`UI_COLLAPSE_KEY`) — свёрнутые локации в интерфейсе;
   - `exofeed_engineer_pin` (`ENGINEER_PIN_KEY`) — PIN инженерного режима;
   - `exofeed_custom_species` (`CUSTOM_SPECIES_KEY`) — пользовательский список видов;
   - `exofeed_db_modified_at` (`DB_MODIFIED_KEY`) — метка времени последнего изменения (используется при импорте для сравнения версий);
   - `exofeed_incubation_reminders_shown` (`INCUBATION_REMINDER_KEY`, с v1.8.2) — какой кладке в какой день уже показали напоминание (дедупликация "раз в сутки").
   - `exofeed_pending_batches` (`PENDING_BATCH_KEY`, с v1.8.7) — активные пакеты отмены массовых действий (5-минутное окно). Специально НЕ включён в бэкап/импорт — короткоживущий, привязан к конкретному устройству/моменту, восстанавливать его из старого бэкапа было бы бессмысленно и путано.
3. Миграция старых структур данных — в функциях `normalizeCell()`, `normalizeAnimal()`, `normalizeClutch()` (с v1.8.0), `migrateBlock()`. Каждое новое поле добавляется туда с `if (x === undefined) x = ...` — старые записи без этого поля получают безопасное значение по умолчанию. Если поле не просто добавляется, а **меняет форму** (пример: `clutch.layDate` (дата) → `clutch.layDateTime` (дата+время) в v1.8.2) — старое поле конвертируется, а затем **удаляется** (`delete clutch.layDate`), не остаётся мёртвым дублем.
4. **Каждая новая версия обязана** пройти тест "старая база версии N-1 корректно читается версией N" — это не опционально. По возможности — тест именно с той версией, что реально задеплоена на GitHub Pages на момент правки (не абстрактной "предыдущей"), т.к. это единственный сценарий миграции, который случится в реальности.
5. `<title>`, `.version-tag`, `CURRENT_DB_KEY`, `legacyKeys`, `version` в объекте бэкапа (`downloadBackupFile`) обновляются **всегда**, для любой версии — даже чисто визуальной/косметической правки (CSS, размер поля и т.п.). Расхождение версии в `<title>` и в `CURRENT_DB_KEY` не допускается.

### Логика утилизации КО (v1.6.0, доработана в v1.8.3/v1.8.4/v1.8.9) — "Расход КО"

- Предубит/разморозка → утилизирован (`utilized: true`) **всегда**, независимо от исхода, `diedCount` для них всегда 0 (понятие "погиб" неприменимо — уже не живой). Массовая кнопка «Не съедено» в утренней проверке (v1.8.3) применяет это же правило пакетно.
- Живой + съеден (полностью/частично) → утилизирован в съеденной части всегда.
- Живой + не тронут полностью или частично → **с v1.8.9** не бинарный вопрос "жив/погиб" на весь остаток, а числовое поле `diedCount` — сколько из непойманного остатка реально погибло за ночь (остальное, `count - eatenCount - diedCount`, посчитано как выжившее и не идёт в расход, можно переиспользовать для другого кормления обычной новой записью). `utilized = (eatenCount + diedCount) > 0`. Поле показывается в индивидуальной карточке при ЛЮБОМ непойманном остатке (`eaten < count`), не только при `eaten === 0` — раньше вопрос "жив/погиб" был виден только при полном отказе, что не позволяло отразить "съедено 1 из 3, из оставшихся 2 один погиб".
  **Массовая утренняя проверка (кнопка для живого КО, v1.8.4) сознательно НЕ детализирована** — там по-прежнему бинарный переключатель "Жив"/"Погиб" на весь выбор (пользователь явно решил не усложнять массовое действие). `resolveNightFeedCore` поддерживает оба вызова: новый параметр `died` (число, из индивидуальной карточки/формы правки) и старый `aliveAfter` (булево, из массовых кнопок) — если `died` не передан, он выводится из `aliveAfter` (`false` → весь остаток погиб, `true` → никто), это в точности воспроизводит прежнее поведение массовых кнопок без изменений.
- Срыгивание → утилизирован всегда.
- В отчётах колонка называется **"Расход КО"** (не "Утилизация" — переименовано в v1.7.0). С v1.8.9 текст колонки для живого КО с частичной гибелью показывает точное распределение (`formatUtilizedText_()`, например "Съедено 1, погибло 2, живо 1") вместо грубого "Да"/"Нет"; расчёт суммы расхода в `aggregateFeedingData` — `eaten + diedCount` для живого КО, `count`/`0` по `utilized` для остальных (не изменилось).
- **Миграция старых записей (до v1.8.9):** если запись была отмечена старым бинарным "Погиб" (`koState==='live', utilized===true, eatenCount===0`, уже разрешённая) — `diedCount` при загрузке выставляется равным всему непойманному остатку (`count - eatenCount`), чтобы суммы расхода в уже накопленных отчётах не "уменьшились" задним числом после обновления версии.

### Инкубация (v1.8.0–v1.8.2) — ключевые архитектурные решения

- Блок-инкубатор — это `block.type === 'Инкубатор'` (константа `INCUBATOR_BLOCK_TYPE`), та же структура `rows`/`cells`, что у обычных стеллажей. Единственный тип блока, где `type` реально ветвит поведение кода (везде ещё это просто лейбл).
- Ячейки инкубатора вмещают **только кладки** — животных туда нельзя переселить/скопировать/восстановить из архива (фильтр `b.type !== INCUBATOR_BLOCK_TYPE` в `renderTransferBlocks`/`renderCopyBlocks`/`renderRestoreBlocks`). В одной ячейке может быть несколько кладок одновременно — это нормальный, а не крайний случай.
- `block.targetTempLog` (режим, с гистерезисом min/max) и `clutch.paramLog` (фактические наблюдения температуры+влажности) — два принципиально разных журнала, не путать при доработках. Первый нужен "для сверки", второй — фактические измерения.
- Вылупившиеся особи заводятся **вручную** через обычную форму добавления животного — никакой автосвязи между кладкой и новой записью `animal` нет, это осознанное решение.
- Привязка родителя к кладке — **снимок** данных на момент выбора (`parentRefs`), не живая ссылка, потому что у животных в базе нет стабильных ID (адресация только позицией в массивах). Если после привязки животное переедет/будет отредактировано — в кладке останется то, что было на момент привязки.
- Визуальное выделение инкубатора — бирюзовый (`--incubator: #00897b`), выбран специально НЕ из уже занятых цветов (`--blue` = обычная занятая ячейка, `--green` = вылупилась/успех, `--red` = погибла/удаление/опасность повсюду в приложении, `--gold` = инженерный режим + частично вылупилась, `--purple` = массовое кормление). При любой новой цветовой кодировке — сверяться с этой таблицей значений, не занимать чужой смысл.
- Напоминания об инкубации (v1.8.2) — `collectIncubationReminders()` считает кандидатов (статус активный, срок указан, `daysElapsed >= estimatedDays - 7`), `startIncubationReminders()` запускается через `setTimeout(..., 5000)` после первого `render()`, показ каждого баннера 10 сек / закрытие тапом, между несколькими в очереди — пауза 3 сек. Дедупликация "раз в сутки на кладку" — через `reminderShownMap` в `exofeed_incubation_reminders_shown` (не версионный ключ).

## Ключевые архитектурные решения (не переизобретать, если попросят похожее)

- **PIN на инженерный режим** — защита только от случайного нажатия, не от целенаправленного обхода (статичный клиентский файл, пользователь честно предупреждён). Структурные/деструктивные действия — под `class="edit-ui"`, видны только в инженерном режиме.
- **Календарь и подсветка по дате** — `calendarPreview`, временно перекрашивает реальный стеллаж, не дублирует схему.
- **Массовое кормление** (`massFeedState`) — ограничено ОДНИМ стеллажом одновременно, осознанно.
- **Массовая утренняя проверка** (`morningCheckState`) — тоже один стеллаж, но НЕ через выбор ячеек галочками (это разные по природе задачи): список уже известных записей "оставлено на ночь" собирается сам, у каждой строки — чекбокс. Три кнопки массового действия (v1.8.3/v1.8.4): "Съедено полностью" и "Не съедено" — только для предубитого/размороженного КО; "Применить выбранное" для живого КО — по индивидуальному переключателю "Жив"/"Погиб" у каждой строки. Смешивать эти группы в одной кнопке нельзя — живой и не-живой КО подчиняются разной логике утилизации (см. выше).
- **Открытие ячейки** — нативное событие `click`, не ручное отслеживание жеста. Кастомный `pointerdown/move/up` — только для drag-and-drop в инженерном режиме (`attachCellDragHandlers`).
- **Перестановка локаций/стеллажей** — кнопки ▲/▼, сознательно НЕ drag-and-drop.
- **Крестик закрытия модалок** — инжектится `initModalCloseButtons()` во все `.modal` при старте.
- **Отчёты** — генерируются как отдельный самодостаточный HTML через `wrapReportDocument()`. `showReportModal(title, bodyHtml, filename, downloadBodyHtml?)` — необязательный 4-й параметр для отчётов с интерактивными элементами (выпадающие списки, кнопки копирования), которые не имеют смысла в статичном скачиваемом файле; если не передан — используется `bodyHtml` для обоих случаев.
- **Общая логика подсчёта отчётов** — `aggregateFeedingData(loc, startMs, endMs)` используется и отчётом за скользящую неделю (`openWeeklyReport`, `endMs = Infinity`), и отчётом за календарную неделю (`openCalendarWeekReport`, границы понедельник–воскресенье). Рендер вынесен в `renderTypeSummaryTable`/`renderSpeciesSummaryTable`/`renderChronoTable` — переиспользуются, чтобы правки не расходились между отчётами. Отчёт по инкубации (`openIncubationReport`, v1.8.0) — по тому же паттерну `showReportModal`.
- **Поля заметок/причин/комментариев** (v1.8.5) — все текстовые поля этого рода (комментарий и причина при ночном разрешении/утренней проверке, родитель/комментарий у кладки, своя причина архивации, инлайн-правка комментария в истории лога) — многострочные `<textarea>`, не однострочный `<input type="text">`. Общий CSS-стиль (тёмная тема) висит на селекторе `input, select, textarea` — если добавляется новое текстовое поле такого рода, использовать `<textarea rows="2">`, а не `<input type="text">`, для единообразия. При рендере значения из данных внутрь `<textarea>...</textarea>` (не через атрибут `value`) — обязательно эскейпить через `escapeHtml()` (экранирует `& < >`; эскейпить только кавычки, как раньше делалось для атрибута `value`, недостаточно).
- **Отображение даты+значения в температурных журналах** (v1.8.6) — единый формат `${formatLogDateTime(ts)}: <b>значение</b>` (двоеточие), НЕ длинное тире (`—`, было так до v1.8.6). Касается трёх существующих журналов (`cell.tempLog`, `clutch.paramLog`, `block.targetTempLog`) и нового `loc.ambientTempLog` — если добавляется ещё один температурный/показательный журнал, использовать тот же формат для консистентности. История кормления (`feed_logs`) этот формат НЕ использует (там `—` перед описанием корма, не значением) — сознательно не трогалось, разные по смыслу записи.
- **Терминология "фоновая температура"** — с v1.8.6 это специфический термин для `loc.ambientTempLog` (температура помещения целиком). Формулировка в модалке показания ячейки (`modal-add-temp`) намеренно НЕ использует слово "фоновая" (было так исторически, поправлено в v1.8.6 на "Температура в этой ячейке...") — чтобы не путать два разных по смыслу журнала при дальнейших правках.
- **Отмена массовых действий** (v1.8.7, `pendingBatches`) — только для массового кормления и 3 кнопок массовой утренней проверки, НЕ для индивидуальных действий (сознательное решение пользователя). Записи адресуются по позиции (`cellIdx`/`animalIdx`/`logIdx`), как и везде в приложении — тот же класс риска при структурных правках во время активного окна (см. предупреждение в истории версий). Каждое массовое действие — свой независимый пакет со своим таймером, несколько пакетов могут существовать одновременно (сознательный выбор пользователя, не "последний заменяет предыдущий"). Данные пишутся в базу СРАЗУ (не черновик/два состояния) — "отмена" технически означает откат к снятому заранее снимку (`prevSnapshot`, для изменённых записей утренней проверки) или удаление только что созданной записи (`isNew: true`, для кормления). Запись, поправленная вручную через обычное редактирование (`markLogTouched`), исключается из отката именно этого пакета, но сам пакет остаётся активным для остальных записей. Обратный отсчёт обновляется тем же `setInterval`, что тикает часы в шапке (`tickClock` → `tickPendingBatchCountdowns`) — без полной перерисовки каждую секунду, только текст бейджа; полная перерисовка — только когда пакет реально истёк.
- **Порядок операций при перемещении/удалении данных между сущностями** (закреплено в v1.8.8 после реального бага с переездом животного) — правило на будущее для ЛЮБОЙ функции, которая одновременно удаляет что-то из одного места и добавляет в другое (трансфер животного — не единственный такой случай, тот же класс риска в принципе может быть где угодно, где есть `splice`+`push` в паре): **сначала проверить, что цель существует и валидна, и только потом удалять из источника**. Ни в коем случае не наоборот — если между удалением и добавлением есть точка, где что-то может пойти не так (пустой список, `undefined`, исключение), удаление, случившееся раньше проверки, необратимо и не отменяется автоматически (нет отдельного отката для одиночных действий — `pendingBatches` покрывает только массовые). При добавлении новых подобных операций — сверяться с этим правилом заранее, а не находить постфактум через баг-репорт, как было с трансфером.
- Русские склонения — `pluralizeRu(n, one, few, many)`.

## Тестирование (обязательный ритуал перед сдачей версии)

`bash` + Node.js + `jsdom` (`npm install jsdom`). После **каждого** значимого блока правок:

1. Извлечь `<script>` блоки, прогнать `node --check`.
2. jsdom-тесты через реальные DOM-события (`dispatchEvent(new win.MouseEvent('click', {bubbles:true}))`), не прямые вызовы функций — так ловятся баги в проводке событий. Исключение — намеренное: заведение вспомогательных данных для сценария теста (например, серия кормлений через `applyFeedingRecord(...)` напрямую, чтобы не писать десяток кликов ради данных, которые сами по себе не являются предметом теста) — это нормально, если сам новый функционал всё равно проверяется кликами.
3. Тест миграции: данные ПРЕДЫДУЩЕЙ версии (а если известно, что именно она уже задеплоена — то именно её) в `localStorage`, прогнать загрузку — сверить поле-в-поле, включая случаи, где поле не просто добавляется, а меняет форму (см. пример `layDate` → `layDateTime` выше).
4. Полный регресс по учётным путям, которые могла задеть правка: создание локации/стеллажа/животного, drag-and-drop, календарь, архив (животных и кладок), поиск, импорт бэкапа. Не обязательно гонять весь регресс целиком при каждой мелкой правке — но явно проверять то, что могло сломаться (пример: правка CSS навигации не требует теста миграции данных, а правка `normalizeClutch()` требует).
5. Тестовые скрипты хранятся в репозитории: `tests/test_v1_8_0.js` — **несмотря на имя файла, это живой, непрерывно дополняемый набор тестов, покрывающий версии вплоть до текущей (сейчас v1.8.9)**, а не тесты только для v1.8.0. Файл не переименовывался, чтобы не терять историю правок — при доработке новой версии дополнять именно его, а не создавать `test_v1.8.10.js` и т.п. При правках, затрагивающих общую логику, явно проверять, что старые тесты на предыдущие версии всё ещё проходят (весь файл прогоняется целиком — это дёшево, там больше 150 проверок).

### Особенности jsdom, уже отловленные (не наступать на те же грабли)

- `new JSDOM(...)` обязательно с `url: 'http://localhost/'`, иначе `localStorage` кидает `SecurityError`.
- `element.innerText` в jsdom **не работает** ни на чтение, ни на запись (тихо ничего не делает) — используй `.textContent`. В коде приложения `showReportModal` использует `innerText` для заголовка — это осознанно не трогалось, при тестировании заголовка проверяй что-то другое (например, `window.currentHtmlReportFilename`), а не `textContent` этого элемента.
- В файле есть `document.write()` (генерация опций года рождения), рассчитанный на исполнение ВО ВРЕМЯ парсинга документа (как в браузере). Если нужно засеять `localStorage` до того, как отработает код инициализации базы — используй `beforeParse(win) { ... }` в опциях `new JSDOM(html, {...})` с `runScripts: 'dangerously'`, а НЕ `runScripts: 'outside-only'` + ручной `eval` скриптов после полной загрузки — это стирает весь документ повторным `document.write`.
- Верхнеуровневые `let`/`const` в `<script>` (`db`, `archiveDb`, `clutchArchiveDb`, `isLocked`, `CURRENT_DB_KEY`, `state`...) — **не** становятся свойствами `window`, в отличие от объявлений `function` (те, включая все функции инкубации/утренней проверки/напоминаний, вызываются напрямую как `win.someFunction()`). Читать/писать переменные можно только через `win.eval('varName')` / `win.eval('varName = ...')`. Рабочий паттерн для записи сложных объектов: `win['__tmp_x'] = value; win.eval('x = window.__tmp_x;')`.
- `URL.createObjectURL` не реализован — стабить вручную (`win.URL.createObjectURL = () => 'blob:mock'`).
- Для pointer-based drag-тестов — стабить `el.setPointerCapture = () => {}`.
- `setInterval` (тикающие часы) держит процесс Node живым — обязательно `process.exit(0)` в конце тестового скрипта (либо явный код возврата через `process.exit(failures === 0 ? 0 : 1)` после подсчёта провалов).
- Реальные `setTimeout`-задержки (напоминания об инкубации: 5 сек/10 сек/3 сек) в тестах **не выжидаются** — тестируются напрямую вызовом функций (`collectIncubationReminders()`, `startIncubationReminders()`, `hideCurrentReminder()`), а не через реальное ожидание таймеров. Это законная, а не урезанная проверка: сама бизнес-логика (кого включать в напоминания, дедупликация, текст) проверяется полностью, просто без траты реального времени на паузы, которые к этой логике отношения не имеют.

## Отложенные направления (НЕ начинать без явного запроса и отдельного обсуждения)

Обсуждались, но не реализуются в текущей архитектуре без отдельного решения пользователя:

- **Аккаунты и права доступа.** Сейчас в приложении нет понятия пользователя вообще — только общий PIN на инженерный режим, один на всех. Обсуждались роли админ/пользователь с закреплением локаций за пользователем и фиксацией авторства каждой записи. Из двух вариантов реализации прав — (а) администратор имеет доступ в инженерный режим, обычный пользователь нет; (б) пользователь может получить доступ в инженерный режим, но с подтверждением от администратора — вариант (а) **существенно проще** (переиспользует уже существующий переключатель `isLocked`, просто источник правды меняется с общего PIN на роль из аккаунта), вариант (б) — это отдельный workflow с очередью заявок. Это была рекомендация, не окончательное решение пользователя — уточнить при возврате к теме.
- **Синхронизация между устройствами.** Обсуждён широкий спектр вариантов: Firebase/Firestore (реалтайм, но требует переписать `save()` с "перезаписать всё дерево целиком" на точечные пути — иначе одновременное редактирование РАЗНЫХ локаций будет перетирать друг друга при каждом сохранении), Supabase, CouchDB/PouchDB (единственный обсуждённый вариант, решающий конфликты слиянием технически, а не дисциплиной пользователя — офлайн-первое хранилище, концептуально ближе всего к текущей архитектуре), P2P/CRDT (Yjs/Automerge, избыточно для масштаба задачи), облачный диск, GitHub-as-storage (коммит = бесплатный аудит-лог), готовый облачный KV-сервис (jsonbin.io и т.п.), Google Sheets (есть встроенная история версий), WebDAV, Nextcloud, Syncthing, Node.js+WebSocket (живое обновление без кнопки).
  **Зафиксированное на данный момент направление (самое простое, выбрано пользователем как финальное после сравнения всех вариантов):** собственный хостинг, один PHP-скрипт (`db.php`) + текстовый `db.json` рядом на диске, без СУБД. `GET` отдаёт файл как есть; `POST` с секретным токеном перезаписывает, предварительно копируя старую версию в файл с датой (дешёвая защита от собственных ошибок). Запись — по нажатию кнопки в приложении ("⬇ Загрузить"/"⬆ Отправить"), **не** фоново/на лету. `flock()` — простая защита от одновременной записи "в упор". Конфликт "кто последний нажал — тот и победил" не решается автоматически — принимается как ограничение, закрывается дисциплиной работы (одновременно редактировать только разные локации), а не кодом. Это большая архитектурная работа (новый компонент — сервер, пусть и минимальный), требует отдельной сессии планирования — не начинать реализацию без явного запроса и подтверждённого плана.
- **Англоязычный форк** — статический перевод текущего приложения без слоя переключения языков, отдельный репозиторий, независимая нумерация версий.

Если пользователь просит продолжить любое из этих направлений — сначала свериться с ним, что план не изменился с момента последнего обсуждения (мог устареть), прежде чем писать код.
